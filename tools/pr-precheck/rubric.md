# Rubric: is this pull request ready to submit?

Grade observable outcomes in the PR package, not its length, formatting, or confidence. The issue, accepted plan, and any explicit deviation note set the intended change; the diff and test evidence show what happened; repository facts set the submission requirements.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| issue-and-plan-fidelity | Issue behavior and material maintainer direction; accepted plan scope/files/approach plus `## Deviations`; every changed diff hunk; description claims read against the diff | The diff implements the issue-relevant work the accepted plan promises, stays within its boundary, and contains no unexplained extra or missing planned work. An intentionally narrower plan can pass when its useful slice is independently testable and the scope clearly names the deferral. If the delivered change departs from the accepted plan, pass only when an updated `## Deviations` note records what changed and why and the description discloses it accurately. Fail for silent scope drift in either direction, unrelated work, or a description contradicted by the diff. | required |
| decisive-test-evidence | Plan's test plan and issue repro compared with actual commands, outputs, added tests, and repo-required local checks in test evidence | Evidence reproduces the reported behavior on the changed path and shows the expected after result, with observable commands and outputs. It includes a relevant regression test or focused test result, plus applicable repository-requested checks, or honestly states a failure/unavailable check with its reason. When the plan names closely related variants implemented with the same fix shape, a reproduced primary case and a regression test covering that shared behavior can establish coverage if the diff shows each variant received the fix; do not demand a separate repro for every variant. Still fail when a distinct planned behavior or material code path has no relevant evidence, evidence is only an assertion, only an unchanged/control path runs, or success is claimed without output. | required |
| diff-reviewability | Full diff and commit summaries, read against the planned change | The issue-relevant change is reviewable without material unrelated hunks or debugging debris. Fail for leftover debug output, dead experimental code, commented-out attempts, or unrelated formatting/restructure churn that materially obscures the change. Do not fail ordinary formatting needed by the change or judge solely by commit-message polish. | required |
| repository-standards | Candidate title/description and diff compared with the repo's PR template, contribution guide, thread requests, and explicit policy in repo facts | The description addresses each applicable required template section and checklist item, links the correct issue, and the diff includes explicitly required artifacts (such as a changelog entry). It follows explicit maintainer constraints and discloses AI use when the repo requires it. Do not require an AI disclosure where no policy asks for one, or mark pre-open CI as passed. | required |
| description-evidence-alignment | Each factual claim in title/description compared with diff and test evidence | The description accurately states what changed, what was tested, and what remains deferred; it does not overclaim a fix, test, CI result, or plan fidelity. A clearly disclosed limitation is acceptable when it matches the plan/deviation record and the delivered slice remains useful and tested. | required |

## Verdict rule

Accept (ready to submit) only when every required check passes. Any required `fail` or `unclear` means reject (hold). Preferred checks, if added later, may give feedback but never change the verdict. Do not infer missing proof or requirements: unclear evidence fails a required check.
